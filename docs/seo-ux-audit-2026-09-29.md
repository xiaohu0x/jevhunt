# JevHunt 用户体验、技术质量与 SEO 增长方案

审计日期：2026-09-29。证据基线：生产站 `https://jevhunt.com` 与当日仓库代码。本文是可评审的实施方案，不代表所有建议已经上线，也不承诺搜索排名或流量。

## 1. 产品目标与判断

JevHunt 应成为帮助开发者“找到适合自己的 Jev 项目，并判断是否值得使用”的专业目录。收录数量是覆盖能力；项目解释、可靠证据、有效筛选和顺畅的下一步，才是用户选择本站的理由。

优先完成以下闭环：

> 从搜索引擎或首页进入 → 按需求筛选 → 理解项目用途及与 Jev 的关系 → 查看证据或访问仓库 → 比较其他选择 → 返回保存的浏览状态。

不把“停留更久”单独设为目标。用户迅速找到合适仓库并离站，可能是成功；找不到分页、反复点无效链接而停留更久，则是失败。衡量成功发现率、详情到仓库点击率和回访，并用停留时长辅助解释。

当前基础已有服务端 HTML、可访问的项目详情、分类页、证据链接、15 个界面语言版本、持续同步和历史状态。下一阶段的优先级是修复真实用户旅程、提高数据可靠性，再建设有独立价值的搜索入口。

## 2. 已测事实与限制

以下为审计时的快照，不能当成永久状态。HTTP 耗时来自本机经网络访问生产的单次样本，包含网络路径影响，不是 Lighthouse 分数，也不是真实用户 Core Web Vitals。本文未读取 Google Search Console（GSC）的点击、展现、索引覆盖或查询数据，因此不声称目前已获得多少自然流量、多少页面被 Google 收录。

| 观察项 | 当时证据 | 用户与增长影响 |
| --- | --- | --- |
| 生产项目数 | `/api/catalog/status` 和 `/api/health` 返回 4,602 项 | 以 live 目录为当前展示依据 |
| 静态快照 | 本地浏览器目录快照为 3,906 项，快照时间为 2026-09-24 | 回退内容与 live 存在差异，需要明确版本和统一渲染 |
| 首页分页 | 原代码将 `visible` 增至 40，但渲染 `list.slice(0, visible)` | “第 2 页”仍显示第 1–40 项；用户感知与页码不符 |
| 首次搜索和筛选 | 非默认筛选、排序或下一页会触发全量目录请求 | 用户第一次想找东西时，才承担最大下载等待 |
| 全量目录响应 | `/api/catalog?all=1`：gzip 下载 540,862 字节；解压 2,355,668 字节 | 移动网络的交互成本偏高，项目增长后继续恶化 |
| 全量刷新 | 已加载完整目录后，前台每 300,000 毫秒再次调用全量获取 | 留在页面的用户会重复下载；应先探测版本 |
| HTML 缓存 | 首页、中文首页、浏览页和详情页响应均见 `cf-cache-status: DYNAMIC`；HTML 路由没有显式 Cache API 命中流程 | 仅设置 `s-maxage` 不足以证明应用 HTML 已在边缘缓存，当前仍需动态读取 D1 |
| 本机响应样本 | 首页 TTFB 约 1.80 秒，浏览第 2 页约 1.14 秒，英文详情约 1.57 秒；全量 API 约 2.73 秒 | 是排查服务端与网络耗时的信号，不应据此宣称 CWV 合格或不合格 |
| GitHub Search | **2026-09-29 08:55 UTC**，9 组搜索来源均为 `failed`，错误为 `GitHub API is waiting for its rate limit to reset`；2 个社区来源为 `ok` | 搜索发现已接入，但此时处于限流退避；不能声称搜索覆盖已全面完成 |
| 同步错误 | 当时最近 20 轮包含多次 `Response too large` 和一次 `catalog_entries.github_id` 唯一约束失败 | 大响应、仓库更名/转移与身份合并需要专项处理 |
| 健康判定 | 同时 `/api/health` 返回 `ok`；当前规则是心跳新鲜且任一来源在 24 小时内成功 | “服务在线”和“主要发现来源健康”需要分别衡量 |
| 复查容量 | 每分钟最多复查 3 项，即理论上限 4,320 项/日；当前 4,602 项，即使没有发现和重试也需约 25.6 小时一遍 | 不适合暗示全部项目每天完成复查；应按变更和访问热度分层调度 |
| 最旧复查 | 当时 active 项目的最旧 `checked_at` 为 2026-09-25 13:33:37 UTC，距观察约 3.8 天 | 最近发布一批内容，不等于全库刚完成复查 |
| 最近活跃时间 | 日常 HTML 元数据复查没有直接更新 `pushed_at`，`pushed` 沿用 candidate/prior | 最近活跃推荐需要用可靠的上游活动时间排序 |
| 旅程统计 | 首页静态 HTML 配置 GA；原通用详情/目录模板没有同等统计，未见搜索、推荐、项目外链的业务事件 | 原有统计不足以回答用户在哪一步成功或流失 |

## 3. 用户旅程与界面设计

### 3.1 初次进入：三秒内理解本站价值

首屏直接回答：这里有什么、收录多少、如何开始、信息何时更新。搜索与目录应优先于代码演示、时间线和大量介绍内容。

建议首屏结构：

```text
JevHunt       项目目录  使用场景  指南  收录标准       语言  主题

发现值得使用的 Jev 项目
查找应用、SDK、集成与开源替代方案，查看项目用途、活跃情况和来源证据。

[ 搜索项目名称、用途或技术栈，例如 browser agent       搜索 ]

4,602 个已收录项目  ·  目录最近更新：9 月 29 日 08:55 UTC

全部  浏览器自动化  Agent 工具  SDK  应用  研究  …
[项目类型] [编程语言] [维护状态]                  [排序：推荐]

显示第 1–20 项，共 4,602 项

[项目名称 · 一句话用途] [项目名称 · 一句话用途]
[适合谁 / 核心能力]     [适合谁 / 核心能力]
[关系标签 · 最近活跃]   [关系标签 · 最近活跃]
[查看详情] [GitHub ↗]   [查看详情] [GitHub ↗]

                 上一页  1 2 3 … 下一页（仅列表底部）
```

这里的数字和日期是结构示例，正式页面必须读取实际数据。界面保留简单的“最近更新”提示；其语义定义为最近一次目录内容发布。完整扫描时间、来源覆盖与失败记录放在状态页，避免用定时任务心跳替代内容新鲜度。

### 3.2 搜索和浏览：减少操作成本

- 标题、描述与明确的“查看详情”入口进入同一个项目详情；GitHub 保持独立外链行为。
- 真分页每页只展示对应区间，当前页、总页数和总结果数清楚可见；固定页大小，并逐步统一首页、分类和浏览页。
- 搜索、筛选、排序、页码写入 URL；详情返回时恢复条件、结果页与合理的滚动位置。
- 没有结果时保留用户输入，解释当前筛选，提供“清除筛选”“尝试相关词”“提交项目”，避免只显示空白。
- 请求进行中保持已有结果可读，明确显示加载状态；网络失败提供重试，不把 20 条预览误当全库搜索结果。
- 移动端将次要筛选折叠到筛选面板，保留搜索、结果数与当前筛选摘要；键盘焦点、点击区域和对比度一并验收。

### 3.3 项目详情：从数据记录变为选择依据

项目详情应按用户决策顺序组织，而不是把全部字段平铺：

1. **是什么**：项目名、一句话用途、适合的开发者或场景、主要操作按钮。
2. **能做什么**：2–4 项可被仓库文档或代码证实的能力；清楚说明与 Jev 的关系。
3. **是否适合我**：编程语言、许可证、运行方式、归档状态、最近活动、关键限制。
4. **怎么开始**：官方安装/文档入口，必要时提供经过核对的最短示例。没有验证的步骤不伪装成实测教程。
5. **为什么可信**：来源、证据摘录、提交版本、资料检查时间、纠错入口。
6. **接下来去哪**：相似项目和最近活跃项目，说明推荐理由，例如“同为浏览器自动化集成”。

第一阶段优先完善有流量潜力、用途清晰的 20–30 个项目。其余项目保留真实的基础详情；不为填满页面批量生成同义改写，不把仓库星数等同于 Jev 能力或质量评分。

## 4. SEO 页面体系与内容边界

目前没有 GSC 查询基线。下表所有搜索词都是**待 GSC 验证的候选意图**，不包含已确认搜索量或难度。英文与中文先验证，其他语言保留可用界面，不同步铺设 15 套薄内容。

| 页面层 | 用户问题 | 候选搜索词：待 GSC 验证 | 页面应提供的独立价值 | 下一步 |
| --- | --- | --- | --- | --- |
| 核心目录首页 | Jev 生态里有哪些项目？ | `Jev projects`、`Jev AI tools`、`Jev 开源项目` | 清楚定位、覆盖范围、搜索筛选、精选入口与真实更新时间 | 分类或项目详情 |
| 分类意图页 | 我需要某类工具，有哪些选择？ | `Jev SDK`、`Jev browser automation`、`Jev agent tools`、`Jev 浏览器自动化` | 类别解释、适用任务、挑选维度、精选项目和可抓取分页 | 项目详情与指南 |
| 项目品牌词页 | 这个项目是什么，如何使用？ | `agentscope Jev`、`jev-ultrafast`、`项目名 + integration` | Jev 特定用途、证据、限制、开始方式、相关项目；避免仅复制 GitHub 简介 | 文档、仓库、相似项目 |
| 场景指南 | 如何用 Jev 完成具体任务？ | `Jev routing example`、`Jev text classification`、`Jev 内容分类` | 可复现步骤、版本与前提、示例输入输出、失败情况、相关项目 | 示例项目与分类目录 |
| 有依据的对比 | 哪个实现更适合我的条件？ | `Jev SDK Python vs TypeScript`、`Jev local alternatives`、`Jev 本地替代方案` | 明确比较范围、统一维度、来源和日期，区分接口/部署/许可证；性能结论需要可复现实验 | 候选详情与官方文档 |
| 收录方法与状态 | 为什么收录，数据是否可靠？ | 主要服务信任与品牌查询 | 分类规则、证据层级、覆盖限制、纠错流程、来源健康 | 目录与纠错 |

页面建设规则：

- 一个页面集中满足一个明确意图，标题与 H1 准确描述页面，不把多个“最佳”“免费”“2026”关键词拼在一起。
- 分类页加入真实的选择建议；分页页保留独立 URL 和可跟随的链接。不能把所有分页 canonical 到第一页。
- 筛选组合不自动全部开放索引。先让稳定且有需求的分类/场景成为正式入口，避免产生大量相似组合页。
- 站内搜索结果默认服务用户查找；没有独立内容价值的搜索词页面不作为批量 SEO 落地页。
- 项目页的原创价值来自用途解释、核对、限制和证据。描述、标题和正文需共同匹配该语言用户；只翻译按钮不代表完整内容本地化。
- 英文与中文先制作和审核高价值内容，有访问与转化证据后再扩展其他语言。保留合理 fallback，明确资料原文语言。
- `hreflang` 仅指向真实、可访问的对应页面，canonical 指向自身规范 URL。导航、面包屑、语言切换不能生成不存在的地址。
- sitemap 只列可索引且返回 200 的规范页面，`lastmod` 反映对页面有意义的修改；不要因为一次心跳把全部页面标为刚更新。
- 全部 4,602 项若扩展为 15 套语言页，将达到约 69,030 个项目 URL。应按实际可索引内容分 sitemap，并使用 sitemap index；先解决内容价值与维护能力，不把 URL 数量作为增长成绩。
- 使用合适的 `BreadcrumbList`、`ItemList`、软件/源码结构化数据。结构化数据不保证富结果，不添加虚构评价、评分或作者体验。

## 5. 数据和性能的实施设计

### 5.1 搜索与分页

将目录请求改成服务端查询，支持 `q`、分类、关系类型、语言、维护状态、排序和页码。响应包含当前页条目、总数、页大小和数据版本。首页与分类页提供可用的服务端结果，JavaScript 增强交互。真实分页链接可被浏览器、无 JavaScript 环境与抓取工具访问。

起步使用 D1 可索引字段和适合规模的全文检索；先定义检索质量和响应预算，再考虑独立搜索服务。搜索字段优先项目名、repo、用途描述和维护过的标签。增加输入防抖与请求取消，避免旧请求覆盖新结果。

不再让首次搜索依赖 2.36 MB 全库。若保留离线索引作为补充，应成为按需功能。刷新先读取轻量版本；版本未变不下载，版本变化只更新需要的数据。

### 5.2 页面缓存与查询

- 为匿名首页、分类、分页、详情和 sitemap 建立明确的边缘缓存策略，区分语言、规范路径、有效查询及版本；管理和账户 API 继续按其权限处理。
- 缓存命中需要用日志/响应标识和请求量验证，不能只看代码里存在 `Cache-Control`。
- 分类数量、语言列表、全站统计在发布时计算或按版本缓存，不随每个详情请求重复聚合。
- 将 `pushed`、`archived` 等高频过滤排序属性做成可索引字段。为相关推荐生成候选集合，避免每次从 JSON 中全量排序。
- 静态与动态页面使用同一渲染器和同一 URL 规则；形成可回退的版本化目录快照，确保上游失败时仍能浏览。

### 5.3 GitHub 发现与可靠性

- 使用受控凭据访问 GitHub API，分别预算搜索、仓库元数据和证据请求；尊重限流和退避，不能靠频繁重试证明“自动更新”。
- 保留日期切片、分页游标和去重，额外统计每组查询最近完整完成时间、待处理窗口、部分结果标识、候选到有效项目转化率。
- 按 GitHub repository ID 识别仓库，更名、组织转移和旧路径形成一致的别名/重定向关系，处理唯一约束冲突。
- 将轻量元数据刷新与重证据检查拆开；根据最近变更、访问热度和失败状态分层，确保容量与承诺一致。
- 状态页区分服务在线、发现来源退避、证据待复查与覆盖未完成。不要因一个社区源成功而显示主搜索覆盖完全健康。
- 大响应失败进入可观测的重试或人工检查路径，保留已知可用数据；对失败原因、年龄分布和长期卡住的项目设告警。

## 6. 本轮状态与 30 天路线

以下“实施中”由当前协作任务提供，仍需合并、测试与生产验收后才能改为完成；本文不代替发布记录。

| 阶段 | 优先级与范围 | 交付 | 验收 |
| --- | --- | --- | --- |
| 第 1–3 天 | **P0：用户旅程正确性**。真分页、详情导航 404、唯一分页标题、面包屑、GA4 基础路径统计：**实施中，待验收** | 可点击且可返回的目录→详情→推荐路径；正确页码和结果区间；无错误 locale 路径 | 抽样 15 语言核心路径、桌面/移动、无 JS 和键盘；验证分页不重复累计；主路径 0 个内部 404 |

| 第 4–10 天 | **P1：搜索、性能与索引基础** | 服务端筛选分页、小响应、边缘缓存、版本探测；规范 URL、sitemap/hreflang 检查；RUM/GSC 基线 | 首次搜索无需全库；SSR 包含当前页；缓存命中与源请求下降可验证；核心模板抓取正确 |
| 第 8–14 天 | **P1：高价值内容试点** | 英中各 3–5 个分类/场景入口；优先完善 20–30 个重点项目；统一内容与证据模板 | 每页有独立用途、选择建议与来源；内部链接形成完整路径；无大规模同义重复 |

| 第 22–30 天 | **P2：以证据扩展** | 修正有展现但低点击的标题与摘要；补有需求但缺结果的内容；优化最慢模板；评估收藏/最近浏览 | 依据真实查询和行为选择扩展方向；审查 7 日回访；只有验证过的内容模式进入更多语言 |

不在本月默认范围：15 种语言批量写同质文章、没有统一实测的性能排行榜、自动生成全部筛选组合落地页，以及为提高停留而增加干扰弹窗。

## 7. 验收指标与测量方法

### 7.1 技术质量

| 指标 | 目标/方法 | 当前状态 |
| --- | --- | --- |
| 核心路径可用性 | 首页、目录、分类、详情、推荐、语言切换、返回浏览，内部 404 为 0 | 本轮修复实施中，待生产验收 |
| 真分页 | 页内条数固定，页 2 为下一个区间；上一页恢复前一区间；总数、页数、筛选匹配 | 实施中，待验收 |
| SSR 与抓取 | 不执行 JS 也可读当前页项目、详情正文和分页链接；状态码、canonical、H1/title 正确 | 需逐模板自动检查与抽样 |
| 可索引页面 | sitemap 规范 URL 返回 200；不包含错误、撤回、搜索噪声或意外重复页；hreflang 对应页可访问 | 需审计并以 GSC 验证实际结果 |
| 移动 CWV P75 | **目标**：LCP ≤ 2.5s、INP ≤ 200ms、CLS ≤ 0.1；按模板、语言、设备收集真实用户数据 | **未测得现场 P75，不是已达标结果** |
| 搜索性能 | 不需先下载全库；建立输入到结果可用的 P75 基线并优化；初步目标 ≤ 500ms，另看慢网首查 | 目标，需埋点验证 |
| 数据覆盖 | 每组搜索完整完成时间、部分结果与限流状态可见；展示 24h/72h 复查覆盖分布 | 当前仅有局部状态，需完善 |
| 故障恢复 | GitHub/D1/单个索引请求失败时，已有目录仍可浏览并提供合理重试 | 需要故障路径验证 |

Lighthouse 可作为每次改动的实验室回归检查；现场 CWV 需要足够真实访问样本。GSC 的索引和搜索数据存在延迟，不用发布后一两天没有变化来判定方案失败。

### 7.2 产品与 SEO 增长

统一事件建议：`search`、`search_results`、`search_no_results`、`project_open`、`recommendation_click`、`outbound_click`、`filter_change`、`pagination_click`。事件携带必要的页面类型、语言、来源位置和结果数；避免把完整任意输入作为无边界的高基数分析维度。

| 指标 | 口径 | 使用方式 |
| --- | --- | --- |
| 搜索成功发现率 | 有搜索的会话中，随后从结果进入项目详情的会话占比 | 分语言、设备、搜索结果数观察；搭配无结果率和外链点击判断 |
| 详情→仓库点击率 | 查看项目详情的会话中，点击该项目 GitHub 外链的会话占比 | 评估详情是否帮助用户作决定；对比入口类型，避免混合误读 |
| 推荐继续浏览率 | 看到推荐模块的详情会话中，点击推荐项目的会话占比 | 必须以模块曝光为分母，避免把没滚到推荐的人算进来 |
| 7 日回访率 | 某日首次访问的可识别匿名设备用户中，接下来 7 天再次访问的占比 | 使用固定 cohort 和相同识别口径；解释跨设备与浏览器限制 |
| 自然搜索有效访问 | GSC 点击、查询、页面与 GA4 自然访问行为结合看 | 分品牌词/非品牌意图、语言、落地页类型；先建立基线 |
| 有展现页面的点击改善 | 相同查询意图下观察展现、位置、CTR 与点击变化 | 不把季节性、排名变化或小样本误当标题改动的因果效果 |

前 7–14 天建立基线，再为提升幅度设目标。本方案不虚构当前 CTR、转化率、搜索量、自然点击或回访率，也不承诺固定时间获得排名。
